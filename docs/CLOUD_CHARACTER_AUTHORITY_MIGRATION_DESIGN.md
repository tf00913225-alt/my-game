## Trusted operation contract (implementation gate)

1. The callable accepts an **intent** (`operationId`, operation type, references, expected serverRevision), never a desired balance, EXP, level, item array, reward total or client timestamp. UID comes only from Firebase Auth. Enforce the active session inside `runProtected()` in the same transaction as all authoritative changes.
2. A single canonical server character schema includes owner UID, immutable character IDs, schema version, revision, server timestamps, balances, item identities, equipped references and claim receipts. The response exposes a complete playable snapshot only when all dependent fields and sidecars are supported. No partial character may set `authoritativeStateReady:true`.
3. Each reward operation recomputes eligibility and amount from trusted server-owned event/progress data. Atomically read the claim receipt scoped to UID + source + period + reward key, then write the receipt, ledger entries, character changes and next revision. A repeated `operationId` returns its recorded result; a different operation ID cannot grant the same unique reward twice. Concurrent stale revisions fail closed. Firestore transaction callbacks must have no external side effects.
4. Battle outcomes, offline duration, ads, dungeon attempts and purchases currently originate in browser code. Session protection alone does **not** make their claims trustworthy. Build a verifiable server event/attempt owner for each before admitting its reward; reject unsupported operation types. Payment rights require payment provider verification independently.
5. On failure or uncertain response, read the operation receipt and authoritative revision before allowing a retry. Never auto-replay a local save after reconnect, use `updatedAt` to break ties, or accept a former device session.

## Existing-save first migration

1. On the original phone, make an immutable UID-scoped backup before any transformation, preserve the existing key, and submit a bounded candidate with a fingerprint. Existing `submitLegacyMigrationCandidate` already labels it `trusted:false`; that label must survive validation. Do not remove the local character or change the startup selection yet.
2. Require an explicit comparison and consent step on the original device. Verify Firebase UID, existing server account, character IDs, schema, equipment references and duplicate IDs. An existing authoritative character or another device's newer server revision causes a conflict screen with no automatic overwrite. A new phone with no local character must never initialize a blank character over that candidate.
3. Structural validation, a fingerprint, a Google login and an active session cannot establish the historical truth of gold, EXP, equipment or already claimed rewards. For older client-only history, there is no independent trusted record to reconstruct it automatically. The owner approved a bounded one-time grandfathered baseline on 2026-09-25; approval of this policy does **not** attest that any particular candidate is genuine or authorize automatic upload or promotion.
4. Only after the selected policy and all future earning/claim operations are implemented: commit a one-time migration marker, initial ledger and complete snapshot in one server transaction, with a UID-unique migration operation ID, expected revision, active session and backup reference. Subsequent migration attempts return the same receipt and never add rewards twice. Preserve the original local backup after acceptance.
5. Switch `resolveSaveFor()` only after server round-trip schema and dependent-state validation, conflict UI and cache backup pass tests. On second phone, read and render the full snapshot; it must not manufacture missing sidecars or claim rewards again.

### Implemented preservation boundary (not admission)

`FourSymbolsAccountSave.createMigrationBackup(uid)` creates a local immutable, fingerprint-addressed record containing exact UID main-save bytes, metadata bytes and registered UID sidecars. It requires the active UID and rejects corrupt sidecars or a conflicting pre-existing record. It is local-only: no candidate is uploaded, no server revision changes, no acceptance marker is written and no save becomes playable in the cloud.

### Approved first-migration policy: guarded historical baseline

- Only a logged-in UID's original device may explicitly present and confirm a complete candidate. Retain an immutable local main-save **and sidecar** backup before submission; keep the original local keys. A private server candidate remains `trusted:false` and is never a playable payload. A subsequent new phone with an empty local cache cannot propose a replacement baseline.
- Validate legacy schema, exactly the supported character IDs, internally consistent levels/EXP/skill points, unique item identities and ownership/equipment references, balance bounds, relic ownership, and every claim-bearing sidecar against the matching main-save record. An absent, contradictory or unsupported claim source fails closed; do not interpret its absence as an unclaimed reward. Record anomalies for review. Validation is consistency screening, **not historical proof**.
- The backend must reject migration if an authoritative character already exists for that UID, if the UID/session changes, or if expected `serverRevision` is stale. The unique UID migration marker, immutable backup reference/fingerprint, initial accepted baseline, provenance=`grandfathered-unverified-history`, claimed/blocked reward receipts, and next server revision must commit together. A same-operation retry returns the same result; a second candidate or a different operation ID cannot mint another baseline. No timestamp chooses between devices.
- For each historical claim source, initialize server receipt/claim state so an already claimed reward cannot be granted again. Where history is uncertain, block that source until independently reviewed; never default to claimable. Keep ledger baseline amounts separate from verified post-migration grants. All later earnings and purchases require server-owned source eligibility and atomic operation receipts; the browser cannot request an arbitrary new gold/EXP/item amount.
- Do not set `authoritativeStateReady:true`, allow another device to restore, or stop local-only play until the complete playable schema, all dependent sidecars, future reward writers, startup conflict handling, backup/recovery, emulator regression, and DEV acceptance are implemented. Old client versions unable to use trusted operations must fail closed for protected writes. This policy acknowledges a one-time unverifiable historical exception and does not weaken the future server authority requirement.
