# First authoritative reward settlement — implementation gate

Status: design and prerequisite hardening only. No gold, EXP, item, claim or playable character mutation is deployed by this contract. `reserveTrustedGrant()` is a pre-migration reservation with `creditedToCharacter:false`; its `grantOperations` receipt is **not** an economy ledger entry or a spendable balance. Do not turn its response into a local award.

## Trusted source and request

The first real reward writer must have a server-owned event/attempt or verified provider record identifying UID, reward source, unique reward key and period, eligibility, canonical reward calculation and expiry/consumption state. A browser may submit only an allowed intent: `operationId`, source reference, expected server revision and active session. The backend derives UID from Auth, checks the current session in the same transaction and computes the reward; reject any client amount, EXP, item list, target balance, `claimed` flag or local timestamp. Start with one enumerated reward path and explicitly reject unsupported sources. Client battle animation or simulated result alone is not proof of eligibility.

## One atomic operation

Within the protected Firestore transaction, read the current envelope, canonical character/economy/inventory state, source record, source-period claim key and `operations/{operationId}`. For a new operation require an exact expected revision, valid source and unclaimed key. Compute the result from server-owned inputs, then write the next canonical revision, bounded playable projection or its fenced rebuild marker, immutable operation receipt, immutable claim record and append-only ledger delta together. If a complete projection cannot be published at the same revision, leave `authoritativeStateReady:false`; never expose a partial character. No external side effects may occur inside a transaction callback.

Receipt identity is UID-scoped and binds `operationId`, operation type, source/key/period, input revision, output revision, result and canonical delta digest. A retry of **the same intent** returns that stored result even when the caller's expected revision is now stale; a different intent reusing the ID fails closed. Another operation ID for the same unique source/key/period cannot award again. A stale *new* operation is rejected. Verify receipt/claim/ledger consistency before responding to retry; missing or contradictory records are `data-loss`, not permission to reissue a reward. Lost responses use receipt lookup and identical retry. Replaced sessions cannot read or retry protected operations.

The ledger records immutable provenance and signed deltas with balance-before/after or asset ownership references; restoration uses a new audited revision and does not delete later receipts, reopen claims or duplicate payment rights. The server enforces bounded document sizes and partitions history by period; the snapshot only contains the compact claim checkpoint needed at startup. If Firestore transaction limits prevent a complete atomic result, redesign the data layout or defer the operation instead of making a partial credit.

## Emulator acceptance before a credit writer

Test identical retry after a lost response, same ID with different intent, different ID for a claimed source, concurrent stale revisions, cross-UID source, revoked session, malformed source, corrupt/missing receipt or claim or ledger, oversized result and an interrupted snapshot build. Assert both the balance/asset delta and exactly one receipt/claim/ledger entry, and that rejected cases change no authoritative document. Payment/refund and offline tickets need their own trusted source checks; this contract alone does not enable them. Require a separately verified server backup/recovery point before `authoritativeStateReady:true` or fresh-device restore.

## Daily check-in server event evidence (2026-10-02)

The existing check-in path records a private immutable `serverUsers/{uid}/rewardEvents/{daily-checkin-YYYYMMDD}` observation in the same protected transaction as issuance or direct credit. It binds the UID, fixed event ID/type, server Taipei day, 50 gold, first canonical character and source revision through a deterministic SHA-256 digest. Grant, reservation receipt and credited ledger carry the same digest. Every daily reservation/credit/replay reads and verifies the event; credited replay also verifies the historical snapshot/archive and delta. No browser completion flag or client amount authorizes it. Missing evidence never permits regeneration of an existing grant or receipt. Previously unbound daily grants stay intact and blocked; an orphan event cannot reopen a claim. This is a prerequisite for unpublished server-created accounts only, not legacy adoption or trusted battle-result validation.


### Original check-in eligibility snapshot (2026-10-02)

The shared event reader also resolves the event's original canonical revision and verifies its complete snapshot against the recovery archive. That source must contain the event's first character in an exclusively server-created one-character account. New issuance checks the current account snapshot pointer against that sealed source. Reservation and retry use the original revision even after current balances/revisions advance; they never replace missing proof with today's account. Missing/corrupt archives or snapshots block with data-loss before writes. Existing valid event digests stay compatible and no old event/source is rewritten. This does not authorize historical admission or provide a trusted combat outcome.

### Battle source preparation (2026-10-03)

Internal `canonical-battle-attempt.js::begin` seals an immutable unpublished first-character source reference, UID, creation session and ten-minute server expiry, with an atomic operation receipt and one-per-source-revision marker. Original snapshot/archive and all three proof records are checked on replay; missing evidence never regenerates, expiry never extends, and another operation or session cannot reopen/inherit that preparation. It does not increment gameplay revision or create a grant/claim/ledger. No public callable or browser hook exists. `outcomeVerified:false` and `rewardEligible:false` are immutable, digest-bound fields. This proof establishes source preparation only: no encounter definition, player actions or combat outcome is verified. A separate server-owned encounter/outcome resolver and its one-time settlement gate remain mandatory before any combat reward or playable integration. No enemy/reward rule is inferred from changing browser monster balance.

### Enemy stat-definition binding (2026-10-04)

Internal `canonical-battle-encounter.js::seal` binds exactly one supported Forest regular enemy stat definition to an existing #785 preparation, in the same session-protected transaction. Its deployment catalog is mechanically generated from the sole MonsterBalance modules and formal Forest identity/level rows; production build/build:check rejects drift. Only two original regular identities are supported. This is not the complete browser roster/rank draw, skill loadout or combat rule policy and must not be treated as a playable encounter.

The transaction creates immutable `battleEncounters/{attemptId}`, `operations/{operationId}`, `battleEncounterAttempts/{attemptId}` and (once per UID/policy hash) `battleEncounterPolicies/{policySha256}`. Each preparation permits only one binding. New binding requires the source revision still current and the original preparation still unexpired; it never changes the preparation or extends its expiry. The shared preparation reader revalidates all original source/receipt/marker/snapshot/archive evidence. Identical replay checks the sealed historical policy and returns the original binding even after later account revisions or expiry; missing proof cannot regenerate. Unknown/currently unsupported enemy references and all browser stat/result/reward fields fail closed.

The seal's immutable `combatRulesReady:false`, `outcomeVerified:false`, `rewardEligible:false`, `creditedToCharacter:false` prevent treating this stat binding as victory or an award. No reward/grant/claim/ledger, gameplay revision, callable, client hook or playable publication is enabled. A future complete server encounter/action/outcome owner and one-time settlement must explicitly consume this evidence and authorize its own successor lifecycle.


### Plain player normal-attack arithmetic (2026-10-04)

Internal pure `canonical-battle-normal-attack.js::resolvePlainPlayerNormalAttack` reuses the original recovery archive/snapshot inspector and sealed enemy-policy inspector. Exact declarations generated from the canonical browser owners compute an unmodified player's base stats, 95% bounded hit, critical check, defense/level/element damage and target HP delta. Production build/check prevents handwritten rule drift. RNG is an explicit bounded server transcript: MISS consumes one sample; a hit consumes hit, crit and damage samples. Missing/extra samples and unsupported modifiers fail closed, with no mutation of the inputs.

Admission supports only a single server-created unequipped character with no skills/effects/defense/bonus resources against a regular original Forest definition. It deliberately excludes enemy turns, tutorial outgoing damage, initiative, skills, statuses, shields and a complete battle outcome. Current player stat coefficients remain the current runtime values, not the distinct future MonsterBalance level contract. V140/V149/V152/V173.64 critical compatibility paths are tested for delegation on this admitted case.

This module has no request handler or writer. A future protected caller must privately fetch and bind the original preparation/seal/session/revision/time, pin the original rules version and seal server RNG before execution. Never accept browser-provided sources or entropy, and never reroll retries. The arithmetic digest alone is not server-origin proof, a legal turn, victory or reward entitlement. No new persistent schema, grant, claim, ledger, source revision or ready-for-publication marker is produced; all readiness/outcome/reward flags remain false. Full action/result adjudication and once-only settlement remain mandatory.

### Protected plain-player attack proof (2026-10-04)

Internal `canonical-battle-attack-proof.js::seal` adds one UID-private arithmetic observation per preparation. The shared `canonical-battle-encounter.js::readSeal` and preparation reader verify the original immutable preparation, source snapshot/archive, encounter, receipts, markers and private enemy policy in the same protected transaction. Original #785/#786 records and digests stay compatible; no preparation or stat seal is rebuilt. The kernel's server sampler adapter shares the exact #789 admission and arithmetic owner.

New intent accepts only operation/preparation IDs and expected revision. Before the transaction a cryptographic 18-byte entropy pool is captured once; transaction retries reuse it. The kernel consumes only the needed hit/crit/damage samples (one on MISS, three on hit). The transaction atomically creates `battleAttackProofs/{attemptId}`, `battleAttackAttempts/{attemptId}`, `operations/{operationId}` and once per policy digest `battleAttackPolicies/{rulesPolicySha256}`. Proof binds the original sources/session/expiry, exact generated rules policy and consumed random transcript/output digest. New proofs require current source revision and original time window. The public return shape exposes metadata only, never private entropy/output.

Identical replay verifies all original source/seal/proof/policy/receipt/marker evidence and returns the original record after later revisions, expiry or deployment rule changes; it does not execute a new deployment's formula against historical output. The original projection is a digest-bound immutable observation, not a portable executable policy. Missing or inconsistent proof fails closed; another operation cannot reseal the preparation or repair missing evidence. All combat/outcome/reward/credit flags remain false. This does not declare a legal turn, mutate player/enemy HP, determine battle victory, provide repeated combat, issue rewards, adopt old sources, publish a playable character or enable another device. Full roster/initiative/enemy/tutorial actions and complete deterministic adjudication are still prerequisites for one-time settlement.
