# Canonical character schema and recovery gate — internal writer only

`users/{uid}/saves/current`: small public envelope with owner, schema, `serverRevision`, `authoritativeStateReady`, materialized snapshot revision/hash/reference and timestamps. Do not append receipt/claim maps to this document. The existing version 2 envelope remains `authoritativeStateReady:false`; the planned canonical schema version is a **separate** version and does not silently upgrade that envelope.

## Planned canonical schema v1 (no public character writer)

All paths below are **planned**, not existing character stores. Every record has `schemaVersion`, `ownerUid`, server-owned revision/provenance and server timestamps where applicable. Reject unknown required fields and unsupported versions; do not infer ownership from a browser-provided UID. A future migration must map every gameplay-critical entry in `PERSISTED_STATE_REGISTRY.md` before declaring the projection complete.

- `serverUsers/{uid}/account/current`: server-owned character slot order and creation status. Exactly three **slots** exist, with slot 1 required and slots 2/3 nullable until created. Slot 3 cannot exist without slot 2. A valid one- or two-character player must not be rejected for lacking later characters. The legacy `player.id` is the player's display name; future stable `characterId` and slot ownership must be server-issued and cannot be changed by renaming.
- `serverUsers/{uid}/characters/{characterId}`: slot, display name, original element, level, EXP, progression, attributes, skill levels/loadouts and schema version. Slot IDs and character references must be unique and agree with the account record. Do not trust historical EXP or levels merely because the structure parses.
- `serverUsers/{uid}/economy/current`: formal gold and currency balances with a revision; no browser-supplied target balance. The first actual mutation requires an operation ID, expected revision, trusted source, transaction, immutable receipt and ledger entry in the same protected operation.
- `serverUsers/{uid}/inventory/{ownedItemId}`: server-issued ownership identity, definition ID, quantity and acquisition provenance. Equipment in `equipment/{characterId_slot}` references an owned item ID, character ID and legal slot; it never duplicates ownership. Relics in `relics/{relicId}` record ownership, level and loadout references. All references must resolve for the same UID before a playable projection is built.

Legacy-to-canonical equipment mapping must enumerate **both** `inventoryItems` and the full objects in `characterEquipment`: the current runtime removes an item from the bag when equipping and returns it on unequip. `item.id` may be a shared definition ID (for example starter gear), while `v141Uid` is a legacy instance marker that can be absent or client-edited; neither is a server-issued ownership proof. The first character currently uses legacy equipment owner key `fire` even when its displayed element differs; later characters use `player2` and `player3`, and older slot aliases (`weapon`/`helmet`/`accessory`) normalize to (`hand`/`head`/`ring`). Preserve and explicitly reconcile any nonempty unmapped owner rather than dropping it. After structural screening and explicit baseline acceptance, assign a new server-owned ID to each distinct item object and store equipped references against those IDs in canonical ownership. Duplicate legacy instance markers, ambiguous alias slots, wrong item types or orphaned character owners block adoption pending review; a matching marker never proves historical entitlement.
- `serverUsers/{uid}/progress/{source}`: quest, dungeon, Boss, tower and abyss progression, with source-specific schema and server period where needed. `claims/{source-period-rewardKey}` is a separate immutable unique claim/blocked-history record; `operations/{operationId}` is a separate idempotent result receipt; `ledger/{period}/entries/{operationId_entry}` records balance/asset deltas. Never grow claim, operation or ledger history in the envelope or one snapshot document. A restoration must retain claim and operation history so old rewards cannot reopen.

The live save also writes optional `allyFormation` via `js/battlefield-slot-owner.js`; its serializable version 1 map binds character indexes 0–2 to unique `ALLY_*` positions. Candidate validation must preserve that field instead of rejecting an otherwise valid save. Read-only screening blocks duplicate slots, invalid slots and references to uncreated characters. Historical saves without formation may need a presentation default later, but that default is not evidence of ownership or rewards. Screening also flags absent gold/shared EXP, skill-loadout or relic/loadout sources rather than manufacturing a partial canonical character. These are structural checks only: the skill/relic contents, historical balances and reward provenance remain unverified. No canonical writer or playable projection is enabled by these checks.

## Materialized playable projection and consistency gate

`serverUsers/{uid}/playableSnapshots/{revision}` is a server-built, bounded projection of canonical records for fast startup. It includes all three slot positions (unused slots explicitly `null`), their complete created-character fields, economy, inventory, equipment, relics, gameplay progress and the claim state needed to prevent replay at startup. Historical receipts and ledger remain separate. A snapshot carries owner UID, canonical schema version, source `serverRevision`, server-generated digest/size and source references; it is never accepted from an uploaded local JSON. Use a server-owned current-snapshot pointer only after all source records and claim checkpoints match the same revision. If any required source is absent, corrupt, oversized or cross-UID, leave the envelope unready and fail closed.

Firestore's standard document maximum is 1 MiB ([official quota](https://firebase.google.com/docs/firestore/quotas)); set an internal size budget below that limit and measure real three-character inventory/claim fixtures before choosing a numeric budget. Do not index a large raw snapshot/backup map when queries only use metadata; verify query usage before adding single-field index exemptions. If complete projection or recovery evidence cannot fit the safe budget, use immutable Cloud Storage objects with Firestore digest/size/schema/reference metadata instead of truncating a character or claim source. This storage decision is pending measurement; no index change or Storage writer is enabled here.

Migration candidates (`trusted:false`) stay private and distinct from: (1) explicitly accepted baseline, (2) ongoing authoritative canonical state, and (3) independently retained recovery snapshots. For large candidate bundles prefer immutable Cloud Storage objects plus Firestore metadata after estimating real save sizes; until then the callable rejects oversized bundles. No index config is activated in this design change.

Before ready=true: create server-owned snapshot history and retention; verify backups cover account, economy, inventory, equipment, relics, progress and claims; define restore point/revision and operator authorization; restore into a fresh revision with an audit receipt; detect corruption by digest; rehearse accidental overwrite, Firestore corruption, cleared localStorage, entirely new phone, stale simultaneous revisions, lost operation response and payment entitlement preservation. Snapshot rollback cannot roll back operation IDs or reopen unique claims. Record outcome and exact snapshot revision used for every recovery.

Recovery point manifest design: record source revision, the exact canonical document/object references and digests for all required domains, creation time, retention policy and an independent claim/operation checkpoint. Verify each referenced object before marking the point usable. Operator restore first selects and verifies a point, then writes a **new** revision with an audit receipt and compensating policy for any later operations; it never deletes later receipts or silently reopens claims. Firestore scheduled backup/PITR is database-level protection and does not replace this game-level point/claim reconciliation. A private migration candidate or local immutable copy is not a server-owned recovery point. No server recovery point or restore operation has been implemented yet.

Executable acceptance skeleton for the first writer/reader PR: valid one/two/three-character slots; missing slot 1 and slot gaps; duplicate stable IDs; UID mismatch; missing economy/inventory/equipment/relic/progress/claim source; equipment or relic reference to unowned ID; snapshot digest/size corruption; stale source revision; operation response lost and retry; restore with later unique claims/payment entitlements; cleared original phone and blank second device. Each invalid or partial case must keep `authoritativeStateReady:false`. These cases are a gate for future implementation, not tests claimed to pass today.

`functions/src/canonical-source-writer.js` adds an internal, protected Firestore transaction primitive for a **new server-created first character only**. It checks that the Phase-2 envelope has no migration candidate or canonical account, requires a server-owned pure source factory and zero initial economy/assets/claim history, verifies all required domains through `assembleCanonicalSnapshot()`, then atomically creates source documents, an unready snapshot and an idempotent operation receipt at one revision. It is deliberately not exported as a callable or connected to `createCharacter()`; there is no authorized browser path to supply its sources or create a playable character. The public envelope remains version 2 and `authoritativeStateReady:false`. A future trusted creation owner must validate the game's ten attribute points, skill starter state, names and element, handle complete ongoing mutations and recovery, then wire a callable/client flow. This internal primitive is not legacy candidate admission, a backup or a second-device restore.
