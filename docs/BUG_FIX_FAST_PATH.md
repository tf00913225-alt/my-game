# Bug Fix Fast Path（Bug 快速修復路徑）

生效日期：2026-10-01。適用於《四象江湖傳》所有一般 Bug 修復工作。

## 一、核心原則

一般 Bug 預設採用「最小必要調查＋最小安全修正」。禁止在沒有證據的情況下，把單一 Bug 自動升級為 Repository（程式庫）全面審計、Owner Convergence（控制來源收斂）或大型架構重構。

目標流程：最新 dev → 重現／確認症狀 → 找出直接根因 → 最小安全修正 → 必要驗證 → PR（合併請求）→ CI（持續整合）→ 合併 dev → 結案。

## 二、一般 Bug 的預設施工流程

1. 取得即時最新 dev HEAD（最新提交）。
2. 確認是否已有同目的有效 PR／工作分支，避免重複施工。續接時保留有效成果，先核對與最新 dev 的差異，不重建同目的 PR。
3. 新工作從最新 dev 建立 fix/ 工作分支。
4. 優先調查直接相關的 Runtime（執行層）、DOM（文件物件模型）、CSS（樣式）、Event Handler（事件處理）、State（狀態）、Data Flow（資料流）與直接呼叫鏈。
5. 找到可被證據支持的直接根因後，立即進入最小修正。
6. 只修改解決該 Bug 必要的檔案與邏輯；優先直接修正既有正式來源。
7. 執行與該 Bug 直接相關的最小必要測試。
8. 建立 PR，等待必要 CI。
9. DEV PR 自動整合統一依 `AGENTS.md`「DEV PR 自動整合規則」：最新 Head 必要 CI／驗收與安全 Gate 通過後自行合併 dev，不需再次要求人工 MERGE-DEV 授權。本路徑不另建合併批准規則。

## 三、禁止預設執行的事項

一般 Bug 不得因「可能」存在架構問題，就預設執行：

- 全 Repository 搜索所有 Owner。
- 全歷史 Commit（提交）考古或全 PR 歷史審計。
- 全 Lifecycle（生命週期）審計或全模組 Owner Convergence。
- 大型 CSS／UI（介面）架構重構。
- Save／Cloud／Runtime（存檔／雲端／執行層）全鏈路審計。
- 與 Bug 無直接證據關聯的技術債清理。

只有直接調查發現明確證據後，才可以擴大範圍。

## 四、升級為架構級施工的條件

只有發現以下任一情況，才將一般 Bug 升級為 Owner Convergence 或架構修復：

1. 同一功能的同一責任存在兩個以上 Runtime Owner（執行控制來源）。
2. Legacy Patch（舊補丁）正在覆蓋目前正式邏輯。
3. Lifecycle 造成狀態被重建、覆寫或延遲更新。
4. 同一資料由多個 Data Source（資料來源）同時控制。
5. Bug 已經修復過，但在相同根因下再次復發。
6. 最小修正會造成其他正式功能回歸。
7. 實際證據顯示問題跨越多個模組，無法由單一 Owner 修正。

升級前必須明確指出：已確認的直接證據、為何最小修正不足、哪些 Owner 發生衝突，以及擴大施工的必要範圍。禁止只因「架構可能不乾淨」就升級。相同症狀本身不等於相同根因；先做直接診斷。

## 五、安全規範維持不變

- main 全程禁止修改；禁止直接寫入 dev。
- 禁止 force push（強制推送）與 rebase（重定基底）。
- 新工作必須從即時最新 dev 建立工作分支，必須經 PR。
- Required CI（必要持續整合）必須實際對應最新 PR Head（最新提交）。
- 不得使用舊 CI 結果替新 Commit 背書，不得把歷史 SHA（提交識別碼）當成最新基底。
- 合併前必須確認無明顯衝突與範圍污染。
- 不得藉修復擅自改玩法、清除玩家資料、降低帳號／雲端權威或金流安全；真正不明確的產品規格仍須釐清。

## 六、CI／工具阻塞處理

修正已完成，但遇到 There are no checks for this commit、Workflow（工作流程）未觸發、GitHub Actions 異常、Connector／API（連接器／程式介面）暫時失敗或部署未產生新版本時，立即分類為 Infrastructure Blocker（基礎設施阻塞）。

不得因 CI／工具問題反覆修改已驗證正確的程式碼。直接診斷並處理 CI／Workflow／API 阻塞，直到最新 Head 得到有效驗證；只能做解除已確認阻塞必要的安全修改，不得繞過必要檢查或安全閘門。外部服務不可用時保留成果並回報具體阻塞證據。

## 七、施工並行限制

同一時間原則上最多 1 個大型架構工程，最多再加 1 個一般 Bug Fast Path。大型工程若正在大量修改共用 Runtime、CSS、State 或 Owner，與其高度重疊的新工程應延後，避免 dev 持續漂移造成反覆重做。

## 八、結案標準

根因已確認、Bug 已修正、對應測試通過、最新 Head 必要 CI 通過、已合併 dev，且合併後 dev 再確認修正仍存在，即可結案。禁止為了「順便整理」延長已完成工程。

驗證必須對應原始症狀：UI／觸控／動畫以最小必要最終畫面與操作驗證；部署／快取特定問題須核對實際目標環境。CI 綠燈不能替代原症狀驗證。沒有取得證據時如實回報目前階段，不宣稱「已修好」。

一般 Bug 結案不包含 dev → main 發布，也不包含無關分支／PR 全面清理。只判定本次工作分支與明確被本次取代的 PR。

## 九、規範優先序與適用範圍

本文件是一般 Bug 的預設施工流程、調查範圍、升級條件、自主整合與結案權威來源。與其他文件衝突時，當次使用者明確指令優先；一般 Bug 的上述事項以本文件為準。

- AUTONOMOUS_REPAIR_CONTRACT.md 的 tests-only（純測試）預設限制、正式 Runtime 即硬停止、固定失敗額度與僅草稿 PR 限制，不適用本路徑內已授權的一般 Bug。
- Owner Convergence Gate 與完整 Lifecycle 審計僅在第四節證據成立、或使用者明確要求架構工程時啟用；不得以「較嚴格規範優先」恢復所有 Bug 全面稽核。
- Change Safety（變更安全）檢查限本次實際修改責任與直接相依；本路徑不允許新增第二 Owner 或以遮蔽代替必要的舊實作退場。
- 原有症狀驗證、資料安全、正式玩法規格與最新 Head 必要 CI 不降低。
- 已明確授權的大型架構工程保留成果與專項要求；本規範不構成重做或丟棄現有工作的理由。
