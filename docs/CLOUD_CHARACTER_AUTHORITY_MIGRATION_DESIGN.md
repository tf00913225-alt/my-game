## Trusted operation contract (implementation gate)

1. The callable accepts an **intent** (`operationId`, operation type, references, expected serverRevision), never a desired balance, EXP, level, item array, reward total or client timestamp. UID comes only from Firebase Auth. Enforce the active session inside `runProtected()` in the same transaction as all authoritative changes.
2. A single canonical server character schema includes owner UID, immutable character IDs, schema version, revision, server timestamps, balances, item identities, equipped references and claim receipts. The response exposes a complete playable snapshot only when all dependent fields and sidecars are supported. No partial character may set `authoritativeStateReady:true`.
3. Each reward operation recomputes eligibility and amount from trusted server-owned event/progress data. Atomically read the claim receipt scoped to UID + source + period + reward key, then write the receipt, ledger entries, character changes and next revision. A repeated `operationId` returns its recorded result; a different operation ID cannot grant the same unique reward twice. Concurrent stale revisions fail closed. Firestore transaction callbacks must have no external side effects.
4. Battle outcomes, offline duration, ads, dungeon attempts and purchases currently originate in browser code. Session protection alone does **not** make their claims trustworthy. Build a verifiable server event/attempt owner for each before admitting its reward; reject unsupported operation types. Payment rights require payment provider verification independently.
5. On failure or uncertain response, read the operation receipt and authoritative revision before allowing a retry. Never auto-replay a local save after reconnect, use `updatedAt` to break ties, or accept a former device session.

## Existing-save first migration

1. On the original phone, make an immutable UID-scoped backup before any transformation, preserve the existing key, and submit a bounded candidate with a fingerprint. Existing `submitLegacyMigrationCandidate` already labels it `trusted:false`; that label must survive validation. Do not remove the local character or change the startup selection yet.
2. Require an explicit comparison and consent step on the original device. Verify Firebase UID, existing server account, character IDs, schema, equipment references and duplicate IDs. An existing authoritative character or another device's newer server revision causes a conflict screen with no automatic overwrite. A new phone with no local character must never initialize a blank character over that candidate.
3. Structural validation, a fingerprint, a Google login and an active session cannot establish the historical truth of gold, EXP, equipment or already claimed rewards. For older client-only history, there is no independent trusted record to reconstruct it automatically. A separate, explicit legacy acceptance policy (for example, reviewed one-time grandfathering with risk limits and a permanent audit marker) must be approved before those values can become authoritative. Without it, keep the candidate quarantined and retain original-phone local play; do not claim secure full preservation.
4. Only after the selected policy and all future earning/claim operations are implemented: commit a one-time migration marker, initial ledger and complete snapshot in one server transaction, with a UID-unique migration operation ID, expected revision, active session and backup reference. Subsequent migration attempts return the same receipt and never add rewards twice. Preserve the original local backup after acceptance.
5. Switch `resolveSaveFor()` only after server round-trip schema and dependent-state validation, conflict UI and cache backup pass tests. On second phone, read and render the full snapshot; it must not manufacture missing sidecars or claim rewards again.
