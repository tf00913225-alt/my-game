有限英雄編隊恢復契約由 `HERO_SYSTEM_V1.md` 的 Hero UI V2 節擁有。既有 account formation 的 v2 以玩家索引／穩定 heroId 保存唯一六格位置，snapshot／archive 檢查正式 owned Hero 及完整玩家參照；v1／null 與歷史原始 bytes 保留。這項 bounded loadout read/write 不發布完整角色、不降低本文件的 migration／recovery／readiness Gate。

`users/{uid}/saves/current`: small public envelope with owner, schema, `serverRevision`, `authoritativeStateReady`, materialized snapshot revision/hash/reference and timestamps. The existing version 2 envelope remains `authoritativeStateReady:false`; the planned canonical schema version is a **separate** version and does not silently upgrade that envelope.

## Canonical schema v1 and current implementation boundary

The assembler and restricted server-created first-character writer implement account, character, economy, inventory, equipment, relic/loadout, progress and claim checkpoint sources with an unpublished snapshot/archive. The callable `createInitialCanonicalCharacter` is connected to the creation flow; limited check-in/potion/shared EXP mutations exist. This is not complete ongoing gameplay authority or a published Cloud Save. Multi-character/Hero authority, complete source coverage and legacy acceptance remain unfinished. The domain paths below are the target model; listing one does not prove its full player acceptance. Every record has `schemaVersion`, `ownerUid`, server-owned revision/provenance and server timestamps where applicable. Reject unknown required fields and unsupported versions; do not infer ownership from a browser-provided UID. A future migration must map every gameplay-critical entry in `PERSISTED_STATE_REGISTRY.md` before declaring the projection complete.

- `serverUsers/{uid}/account/current`: server-owned character slot order and creation status. Exactly three **slots** exist, with slot 1 required and slots 2/3 nullable until created. Slot 3 cannot exist without slot 2. A valid one- or two-character player must not be rejected for lacking later characters. The legacy `player.id` is the player's display name; future stable `characterId` and slot ownership must be server-issued and cannot be changed by renaming.
- `serverUsers/{uid}/characters/{characterId}`: slot, display name, original element, level, EXP, progression, attributes, skill levels/loadouts and schema version. Slot IDs and character references must be unique and agree with the account record. Do not trust historical EXP or levels merely because the structure parses.
- `serverUsers/{uid}/economy/current`: formal gold and currency balances with a revision; no browser-supplied target balance. The first actual mutation requires an operation ID, expected revision, trusted source, transaction, immutable receipt and ledger entry in the same protected operation.
- `serverUsers/{uid}/inventory/{ownedItemId}`: server-issued ownership identity, definition ID, quantity and acquisition provenance. Equipment in `equipment/{characterId_slot}` references an owned item ID, character ID and legal slot; it never duplicates ownership. Relics in `relics/{relicId}` record ownership, level and loadout references. All references must resolve for the same UID before a playable projection is built.

Legacy-to-canonical equipment mapping must enumerate **both** `inventoryItems` and the full objects in `characterEquipment`: the current runtime removes an item from the bag when equipping and returns it on unequip. `item.id` may be a shared definition ID (for example starter gear), while `v141Uid` is a legacy instance marker that can be absent or client-edited; neither is a server-issued ownership proof. The first character currently uses legacy equipment owner key `fire` even when its displayed element differs; later characters use `player2` and `player3`, and older slot aliases (`weapon`/`helmet`/`accessory`) normalize to (`hand`/`head`/`ring`). Preserve and explicitly reconcile any nonempty unmapped owner rather than dropping it. After structural screening and explicit baseline acceptance, assign a new server-owned ID to each distinct item object and store equipped references against those IDs in canonical ownership. Duplicate legacy instance markers, ambiguous alias slots, wrong item types or orphaned character owners block adoption pending review; a matching marker never proves historical entitlement.
- `serverUsers/{uid}/progress/{source}`: quest, dungeon, Boss, tower and abyss progression, with source-specific schema and server period where needed. `claims/{source-period-rewardKey}` is a separate immutable unique claim/blocked-history record; `operations/{operationId}` is a separate idempotent result receipt; `ledger/{period}/entries/{operationId_entry}` records balance/asset deltas. Never grow claim, operation or ledger history in the envelope or one snapshot document. A restoration must retain claim and operation history so old rewards cannot reopen.

The live save also writes optional `allyFormation` via `js/battlefield-slot-owner.js`; its serializable version 1 map binds character indexes 0–2 to unique `ALLY_*` positions. Candidate validation must preserve that field instead of rejecting an otherwise valid save. Read-only screening blocks duplicate slots, invalid slots and references to uncreated characters. Historical saves without formation may need a presentation default later, but that default is not evidence of ownership or rewards. Screening also flags absent gold/shared EXP, skill-loadout or relic/loadout sources rather than manufacturing a partial canonical character. These are structural checks only: the skill/relic contents, historical balances and reward provenance remain unverified. The existing snapshot Owner additionally validates retained skill-loadout structure on durable playable sources and every complete projection: only skill levels/equipped references and an optional nonempty recorded label, positive safe-integer levels within the Client storage ceiling of 10, and at most four distinct references to recorded learned skills. It preserves exact recorded levels, labels and equipped order without defaults, learning, costs, element eligibility or combat execution. Historical v1 sources without the durable playable extension retain their original bytes/hash compatibility; malformed historical loadouts cannot become complete evidence. Skill catalogue identity, per-skill caps, prerequisites and acquisition provenance remain separate unverified gates. These screening checks do not admit historical state; the restricted new-character writer is a separate path and its projection remains unpublished.

Work ID `CLOUDSAVE-ACHIEVEMENT-SOURCE-PRESERVATION-20261013`: the existing snapshot Owner validates retained `achievementState` on durable playable sources and every complete projection as achievement identifiers mapped to explicit boolean claim markers. Empty maps and recorded true/false markers remain exact in snapshots, archives and protected mutation/recovery paths; the reader supplies no defaults, catalogue eligibility, completion calculation, claim creation or reward. Historical v1 records without the durable playable extension retain their bytes/hashes, including malformed historical markers, but cannot become complete evidence. Catalogue identity and reconciliation against retained claim/receipt history remain separate unverified gates; a boolean marker alone is not an entitlement.

## Materialized playable projection and consistency gate

`serverUsers/{uid}/playableSnapshots/{revision}` is a server-built, bounded projection of canonical records for fast startup. It includes all three slot positions (unused slots explicitly `null`), their complete created-character fields, economy, inventory, equipment, relics, gameplay progress and the claim state needed to prevent replay at startup. Historical receipts and ledger remain separate. A snapshot carries owner UID, canonical schema version, source `serverRevision`, server-generated digest/size and source references; it is never accepted from an uploaded local JSON. Use a server-owned current-snapshot pointer only after all source records and claim checkpoints match the same revision. If any required source is absent, corrupt, oversized or cross-UID, leave the envelope unready and fail closed.

Firestore's standard document maximum is 1 MiB ([official quota](https://firebase.google.com/docs/firestore/quotas)); the current assembler enforces a 750 KiB snapshot budget and recovery archive an 800 KiB budget; measure complete three-character/Hero/inventory/claim fixtures before treating those bounds as sufficient. Do not index a large raw snapshot/backup map when queries only use metadata; verify query usage before adding single-field index exemptions. If complete projection or recovery evidence cannot fit the safe budget, use immutable Cloud Storage objects with Firestore digest/size/schema/reference metadata instead of truncating a character or claim source. Full-size acceptance and any Storage fallback remain pending; this contract enables no index change or Storage writer.

Migration candidates (`trusted:false`) stay private and distinct from: (1) explicitly accepted baseline, (2) ongoing authoritative canonical state, and (3) independently retained recovery snapshots. For large candidate bundles prefer immutable Cloud Storage objects plus Firestore metadata after estimating real save sizes; until then the callable rejects oversized bundles. No index config is activated in this design change.

Before ready=true: create server-owned snapshot history and retention; verify backups cover account, economy, inventory, equipment, relics, progress and claims; define restore point/revision and operator authorization; restore into a fresh revision with an audit receipt; detect corruption by digest; rehearse accidental overwrite, Firestore corruption, cleared localStorage, entirely new phone, stale simultaneous revisions, lost operation response and payment entitlement preservation. Snapshot rollback cannot roll back operation IDs or reopen unique claims. Record outcome and exact snapshot revision used for every recovery.

Recovery point manifest design: record source revision, the exact canonical document/object references and digests for all required domains, creation time, retention policy and an independent claim/operation checkpoint. Verify each referenced object before marking the point usable. Operator restore first selects and verifies a point, then writes a **new** revision with an audit receipt and compensating policy for any later operations; it never deletes later receipts or silently reopens claims. Firestore scheduled backup/PITR is database-level protection and does not replace this game-level point/claim reconciliation. A private migration candidate or local immutable copy is not a server-owned recovery point. `canonical-current-recovery.js` implements operator-approved fresh-revision restoration of the current unpublished server-created single-character state, not selection of a historical point or full disaster restore. Existing recovery archives remain `readyForRestore:false`; full game recovery/claim reconciliation acceptance is unfinished.
