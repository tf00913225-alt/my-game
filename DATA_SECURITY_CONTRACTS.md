# Cloud account and save security contracts

Status: architecture contract, 2026-09-26. See `docs/CLOUD_SAVE_IMPLEMENTATION_PROGRESS.md` for what is actually deployed. This contract grants no authority to historical browser data.

1. **Browser boundary.** Firebase Auth identifies a UID; an active game session restricts the current device. Firestore browser writes to official progression remain denied. Neither identity, App Check nor a matching fingerprint proves a client-reported balance, result or reward. The browser requests an operation; the trusted backend decides eligibility and amount.
2. **Client cache.** `four_symbols_save:<UID>` and registered sidecars are UID-isolated local play/cache. Timestamps, `localDirty` and fingerprints do not choose a cloud winner. An offline candidate cannot overwrite a newer authoritative revision.
3. **Server authority.** Account/character ownership, premium/payment rights, economy, inventory ownership and unique claims require backend validation. Client battle rendering and harmless preferences do not need server actions per frame. For a run reward, validate a server-owned attempt and settle once.
4. **Migration candidate.** A sealed original-device backup is the only input to a *new* submission. It names owner UID, backup ID, main fingerprint, complete sidecar manifest fingerprint, schema version and SHA-256 of exact raw bytes. Backend stores it privately as `trusted:false`; even valid digests prove consistency only. The original legacy key and original-phone backup survive adoption. Missing/corrupt claim history blocks that claim; no absent record implies unclaimed. Older candidates without a bundle remain blocked. A candidate is not a disaster backup, accepted baseline or playable state.
5. **Accepted baseline.** An explicit owner-confirmed, one-time grandfathered historical exception may be created only after complete structural/claim screening, UID/session/revision checks and recovery preparedness. An existing authoritative account blocks re-admission. The marker, starting ledger, blocked/claimed reward receipts, full character snapshot and next revision commit in one transaction. Historical amounts remain tagged unverifiable, separate from future verified grants.
6. **Operations.** The first trusted gold/EXP/item mutation must simultaneously have a unique UID-scoped `operationId`, expected `serverRevision`, idempotent receipt, ledger entry, trusted source and transactional character revision. Retries return the same receipt; another ID cannot claim the same source/period/reward. Lost responses require receipt lookup before retry. Transaction callbacks must not perform external side effects.
7. **Snapshots and restore.** Canonical server records are authoritative; a materialized playable snapshot is a versioned projection. Durable recovery snapshots, revisions, integrity checks, restore points and restore audit must exist before `authoritativeStateReady:true`. A restore never replays operation receipts, claim rights or paid entitlements; operator restores are authorized, auditable transactions with revision checks. A local migration safety copy is not a server backup.
8. **UID and devices.** All local/remote state is owner-scoped. An Auth UID change invalidates the previous resolution; a replaced session cannot write. Google upgrade of an anonymous account links the provider to the same UID when available. A Google provider already belonging to another UID raises an explicit account conflict; neither UID is automatically overwritten or economically merged.
9. **Offline.** The policy in `docs/OFFLINE_AUTHORITY_POLICY.md` controls each reward path. Offline progress is a limited candidate or pre-authorized ticket, never a claim that local time or latest save outranks the server. High-value unique claims, payments, refunds/revocations and rare ownership require online authority. A protected old client fails closed.
10. **Payments and audit.** Payment grants require provider verification, unique external-event ID, operation receipt and ledger. Refund/revoke is a compensating audited operation, never a silent snapshot rollback. Preserve a queryable operation/claim history outside the current envelope; avoid unbounded maps in one document.
11. **Fail closed.** Missing/corrupt main save, sidecar, manifest, UID metadata, session, receipt, revision or backup halts the affected migration/claim/restore. Do not create a blank character over an unresolved account, silently delete original keys, or present partial recovery as complete.
