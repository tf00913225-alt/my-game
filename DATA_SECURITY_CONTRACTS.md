# Cloud account and save security contracts

Status: architecture contract, consolidated 2026-10-07; owner-confirmed service scope updated 2026-10-24. See `docs/CLOUD_SAVE_IMPLEMENTATION_PROGRESS.md` and the current Work PR for implementation/deployment evidence. Policy approval is not implementation or player acceptance. This contract grants no authority to historical browser data.

1. **Browser boundary.** Firebase Auth identifies a UID; an active game session restricts the current device. Firestore browser writes to official progression remain denied. Neither identity, App Check nor a matching fingerprint proves a client-reported balance, result or reward. The browser requests an operation; the trusted backend decides eligibility and amount.
2. **Client cache.** `four_symbols_save:<UID>` and registered sidecars are UID-isolated local play/cache. Timestamps, `localDirty` and fingerprints do not choose a cloud winner. An offline candidate cannot overwrite a newer authoritative revision.
3. **Product and authority ceiling.** The product is a **Client-simulated single-player RPG + Cloud Account / Cloud Save**. Client owns ordinary combat simulation, animation, skills, turn flow, HP/SP and RNG. Server owns Auth/UID, active session, account/character/assets/progress, revision, migration, backup/recovery, bounded settlement, unique claims, payment rights, receipts, ledger and idempotency. Ordinary combat must not grow into per-action/per-round Functions, server action RNG, HP/SP lifecycle, skill/status runtime or a battle replay engine without an explicit product decision. This ceiling applies to private/internal prototypes too. Shared/generated formulas do not authorize a second server gameplay execution lifecycle. The approved service requires connectivity and backend persistence of key progress; ordinary battle remains local. `docs/OFFLINE_AUTHORITY_POLICY.md` owns short-disconnection behavior, not a full offline/ticket product. A client win flag is not verified victory; bounded settlement must state that limitation rather than requiring full server combat simulation. High-value paths retain their own online authority gates.
4. **Migration candidate.** A sealed original-device backup is the only input to a *new* submission. It names owner UID, backup ID, main fingerprint, complete sidecar manifest fingerprint, schema version and SHA-256 of exact raw bytes. Backend stores it privately as `trusted:false`; even valid digests prove consistency only. The original legacy key and original-phone backup survive adoption. Missing/corrupt claim history blocks that claim; no absent record implies unclaimed. Older candidates without a bundle remain blocked. A candidate is not a disaster backup, accepted baseline or playable state.
5. **Accepted baseline.** An explicit owner-confirmed, one-time grandfathered historical exception may be created only after complete structural/claim screening, UID/session/revision checks and recovery preparedness. An existing authoritative account blocks re-admission. The marker, starting ledger, blocked/claimed reward receipts, full character snapshot and next revision commit in one transaction. Historical amounts remain tagged unverifiable, separate from future verified grants.
6. **Operations.** The first trusted gold/EXP/item mutation must simultaneously have a unique UID-scoped `operationId`, expected `serverRevision`, idempotent receipt, ledger entry, trusted source and transactional character revision. Retries return the same receipt; another ID cannot claim the same source/period/reward. Lost responses require receipt lookup before retry. Transaction callbacks must not perform external side effects.
7. **Snapshots and restore.** Canonical server records are authoritative; a materialized playable snapshot is a versioned projection. Durable recovery snapshots, revisions, integrity checks, restore points and restore audit must exist before `authoritativeStateReady:true`. Normal load selects the latest valid save through the existing resolver; it is not a historical restore. Historical restore requires support identity verification, preservation of the current state, explicit operator approval and an audited revision-checked transaction whose result the game can actually load. Restore must preserve current order history, cosmetics ownership, month-card expiry, daily-claimed markers and compensation history; it never replays receipts, reopens claim rights or automatically reissues a purchased package. A local migration safety copy is not a server backup. Recovery is best effort within a finite retention window, not a permanent or unconditional guarantee; backup and order-history retention are separate pending decisions. No retention reduction or data deletion is authorized by this policy.
8. **UID and devices.** All local/remote state is owner-scoped. One UID has one effective playing session/device; an Auth UID change invalidates the previous resolution and a replaced session cannot write. Guests use Anonymous Auth and may try the game but cannot purchase. Before purchase the account must have a recoverable formal binding that preserves guest progress. Google upgrade of an anonymous account links the provider to the same UID when available. A Google provider already belonging to another UID raises an explicit account conflict; neither UID is automatically overwritten or economically merged. The existing Auth/link primitives do not prove this complete guest-to-purchase flow is implemented or accepted.
9. **Connectivity.** The policy in `docs/OFFLINE_AUTHORITY_POLICY.md` controls each reward path. Short disconnection retains protected same-UID local state with an explicit unsaved/pending indication, never false server-save success. Reconnect revalidates UID/session/revision; local time or latest local save never outranks the server. Full offline earning and multi-device offline merge are outside the approved service scope. High-value unique claims, payments, refunds/revocations and rare ownership require online authority. A protected old client fails closed.
10. **Payments and audit.** The backend verifies provider payment evidence, binds the order to its UID and permits one formal grant for that order; unique external-event IDs, operation receipts and ledger protect callback/retry idempotency. Payment failure, missing delivery, refund/revoke and manual redelivery must remain queryable. Refund/revoke is a compensating audited operation, never a silent snapshot rollback. Preserve queryable order/operation/claim history outside the current envelope; avoid unbounded maps in one document. Provider selection and the real-payment/grant/support flow remain unimplemented acceptance work, not authority to accept client purchase claims.
11. **Fail closed.** Missing/corrupt main save, sidecar, manifest, UID metadata, session, receipt, revision or backup halts the affected migration/claim/restore. Do not create a blank character over an unresolved account, silently delete original keys, or present partial recovery as complete.

## Service scope and support decisions (2026-10-24)

Prefer simple construction and low maintenance within the account/payment/backup safety floor above. Accept residual cheating risk confined to the player's local stats/materials or local rollback reuse; this is an anti-cheat scope decision, not permission to weaken official payment, claim-once, UID/session, revision or persistence gates, or to promote untrusted local values. No server combat engine or second authority is justified by that residual risk. Existing frozen server battle code and security/regression evidence remain preserved under the construction gate below.

Support starts with small bounded queries and an audit flow, not a large support console. For a material-loss dispute, inspect the original order, delivery and backup evidence first. A verified paid-but-undelivered order must be recoverable through its original unique grant, not a second purchase grant. If evidence remains inconclusive, only a human operator may review a one-package goodwill compensation; record the original order reference, case, reason, decision and result with deduplication so retries/reopened cases cannot become unlimited compensation. This is not automatic compensation or a completed admin capability. Exact operator authorization and execution details remain pending; no privileged endpoint, new IAM access or real grant/restore is authorized here.

### P4 product decisions (2026-10-29)

1. Complete the game, account and save capabilities first; paid sales remain deferred. Choose the payment provider and fees when preparing to sell. Existing payment verification, UID/order binding, unique grants, receipts and refund protections remain required; deferral neither removes them nor marks real-payment acceptance complete.
2. A 30-day game-backup window is the direction, not an activated retention policy. Before implementation, verify backup size, frequency, player count and estimated cost. Payment orders and entitlement records have separate retention and must not be deleted with game backups; their retention period remains undecided. Backups are best-effort recovery, not a promise that every loss can be recovered. This decision authorizes no deletion, retention executor or cloud setting change.
3. Compensation should use a simple controlled tool, with explicit human operator review and user confirmation, recorded case/reason/decision/result and duplicate prevention. Retain the original-order and unique-grant protections above. Do not build a full support backend, automatic redelivery or arbitrary asset writer; precise operator authorization and implementation remain pending.
4. Defer the undecided month-card extra dungeon-refresh benefit; retain already agreed benefits. Do not invent an extra-refresh count or treat this deferral as permission to remove existing rights.

These are product directions, not completed features or acceptance evidence. Existing UID/session/revision and private snapshot/archive/audit primitives remain partial foundations; complete guest binding, playable recovery/Boot and the controlled support workflow remain pending. Actual payment/grant acceptance is deferred until sales preparation, not waived. Player acceptance belongs to `docs/CLOUD_SAVE_PHASE4_CONTRACT.md` and its existing requirement batch. No new fee, privilege, deployment or data operation is authorized by this document update.

## Cloud construction gate

This document is the sole Owner of the product boundary and Cloud authority ceiling; subsystem contracts reference it. Until complete Cloud Save and device recovery acceptance passes, new large Cloud subsystems must be directly necessary to an unfinished player-value acceptance. Schema, private records, unit/emulator success and deployment alone do not complete that acceptance.

Before any Cloud PR, record in its existing Work PR:

1. Which unfinished acceptance does this change directly advance?
2. Would omitting it block full Cloud Save or device recovery? If not, justify its priority against the unfinished milestone.
3. Does it move Client Gameplay to Server?
4. Does it create duplicate Client/Server gameplay formulas or executable maintenance?
5. Does it add a permanent Cloud authority surface?

Yes to 3/4/5 defaults to **STOP** unless an explicit product decision authorizes that specific responsibility. The approved Account/Save responsibilities in clause 3 already authorize necessary canonical writers, revisions, receipts, ledger, migration and recovery within their existing gates; they do not authorize a server combat engine. New gameplay authority outside that boundary needs a product decision before construction.

Existing server battle preparation/encounter/attack proof/opening and repeated rounds/restricted instance/round writer/terminal closure/terminal reader are **FREEZE**: preserve code, private evidence, protected lifecycle, retention and regression/CI; stop successor outcome authority, new combat features, callable/client integration and reward entitlement derived from these prototypes. Attempt/Ticket remains an allowed bounded-settlement design, but these existing restricted preparations are not automatically reusable tickets. Any later retirement requires dependency/data/restore analysis and separate scope. This consolidation grants no deletion, fail-open compatibility or ready=true publication.
